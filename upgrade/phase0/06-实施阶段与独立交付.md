# 06｜Ubuntu 独立客户端、独立交付与 Phase 1–5 实施方案

本文是 2026-11-11 Phase 0 的研究建议，尚未实施。已批准的产品边界来自 [父项目](https://app.notion.com/p/3ff5421e690b81bdae14c0675f0b3acf)、[2.0 子项目](https://app.notion.com/p/4135421e690b815eb404c3024c860134) 和 [Phase 0 Task](https://app.notion.com/p/4155421e690b81829fe6ce746cff195d)。本文中的目录、接口组织、包名细节和验收步骤属于待审的工程方案；Phase 1 开工、正式安装和服务启用仍按各自授权范围执行。

## 1. 推荐结论与现有基础

Ubuntu 保留 **Electron + React + TypeScript + Zustand**。将现有 React 工作区改为 Desktop 自有资源，把网络通信和设备凭据放在 Electron 主进程，通过窄 IPC 接口向 renderer 提供 Gateway 能力；本地历史、草稿、偏好与主题由 Desktop 自己管理。Gateway 包仅包含 API、Codex 适配器、必要状态、CLI 和运行依赖。Android 是独立 Compose 客户端，三组件用版本化协议协作。

## 2. Ubuntu Desktop 具体设计

### 2.1 进程与资源边界

```text
Electron main
  ├─ 打包资源与受信主题资源处理
  ├─ Gateway HTTP/WSS 客户端、凭据、未知操作记录
  ├─ 系统文件选择/保存、通知、窗口状态
  └─ preload：逐方法白名单、参数/返回值校验
          ↓
React renderer
  ├─ Navigation / Conversation / Inspector
  ├─ Zustand：当前页面、事件投影、加载与错误状态
  └─ IndexedDB：历史缓存、草稿、阅读位置、设备偏好

所有 Codex、主机项目与成果操作 → Gateway → 官方 Codex/已授权主机文件能力
```

推荐在 Desktop 自有目录中逐步整合 renderer，保留仓库现有 pnpm/TypeScript/Vite 工具链，不再把它视为 Android 共用网站。Gateway 不提供首页、JS/CSS bundle 或主题管理接口；Desktop 即使在 Gateway 不可达时也能完整启动，显示本地连接页与只读缓存。

正式资源使用受限自定义协议，例如 `oraculum-app://bundle/`。协议只解析打包清单中的本地文件，拒绝非预期 host、路径穿越、编码绕过、符号链接越界和任意本机文件请求；按 Electron session 注册，启用所需 `standard`/`secure` 能力，保持 CSP 生效，不启用 `bypassCSP`。这符合 Electron 对本地页面采用自定义协议的建议，也使 IndexedDB 有稳定的本地 origin。具体使用已锁定版本支持的 `protocol.handle`，不因最新文档出现新 API 而无验证替换。依据：[Electron protocol](https://github.com/electron/electron/blob/v44.9.1/docs/api/protocol.md)、[Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)。

renderer 的网络入口统一改为注入的客户端接口；主进程持有已选 endpoint，执行统一 Gateway HTTP/WSS 协议、限额、超时和恢复规则。renderer 不能传入任意 URL、HTTP method/header、系统命令或主机路径来要求主进程执行。这样同一份 Gateway Schema 可用于 Android 与 Desktop，而 Electron 凭据不必暴露给 Markdown 或主题所处的页面环境。

### 2.2 IPC 与凭据

| 窄接口示例 | 允许的数据/行为 | 必须拒绝的输入 |
| --- | --- | --- |
| `gateway.connect` / `gateway.disconnect` | 连接已登记且经过配置校验的 endpoint ID，返回连接/协议状态 | 任意运行时代码、凭据回读、请求头透传 |
| `project.list` / `thread.read` / `thread.subscribe` | 生成 Schema 校验的 ID、游标、页大小；返回结构化投影 | 未知方法、超限分页、任意原生 RPC passthrough |
| `turn.start` / `operation.get` | 固定的 Gateway 请求结构、`operationId`；主进程负责落盘后发送 | 未经对账再次发送未知写入、改换 payload 后复用 ID |
| `file.chooseUpload` / `artifact.save` | 原生对话框选择本地文件，或通过 Gateway 下载已授权成果；renderer 获得受控句柄和状态 | renderer 指定任意本地绝对路径读取/覆盖、绕过 Gateway 访问项目文件 |
| `theme.install` / `theme.select` | 明确选择的可信 CSS 包，经本地校验后安装/选择 | JS/HTML/可执行文件、扩大资源协议的目录范围 |
| `events.subscribe` | 仅业务事件数据，提供注销函数 | 暴露原始 `ipcRenderer`、IPC event、Electron 对象或任意 channel |

每个 IPC handler 校验 **发送者 webContents 身份、主 frame 身份和允许的 frame origin**，然后运行输入 Schema 校验；iframe、外部页、已销毁 frame 均拒绝。preload 用 `contextBridge` 逐方法暴露接口，事件回调去掉原始 IPC event。保持 renderer sandbox、context isolation、禁用 Node/webview、限制导航及新窗口，原生外链/文件打开仅由明确用户动作触发。官方明确指出隔离本身不能让任意 IPC 暴露变安全；推荐逐消息接口并校验发送者。依据：[Context Isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation)、[Security：IPC sender](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages)。

长期 `deviceCredential` 仅保存在主进程管理的私有存储，用于换取短时内存 access token；renderer、IndexedDB 历史库、日志、通知 payload 不保存长期凭据。首版可使用锁定 Electron 44 的 `safeStorage` 同步小凭据路径，在 `ready` 后验证 `isEncryptionAvailable()` 且 Linux backend 为实际系统密钥服务，拒绝 `basic_text`/未知 backend，也不调用强制明文回退。密钥环暂时锁定时显示可恢复的连接状态，不清除仍有效凭据。后续若采用异步 API，必须验证其 fallback 行为，不能仅凭返回“可用”就认定持久凭据受保护。依据：[已锁定 Electron 44.9.1 safeStorage 文档](https://github.com/electron/electron/blob/v44.9.1/docs/api/safe-storage.md)。

### 2.3 本地状态、历史缓存与退出语义

使用全新 Desktop profile，例如 `$XDG_CONFIG_HOME/oraculum-desktop-v2/`；未设置 XDG 时按平台规范回退。正式 profile 与开发/测试 profile 分离，拒绝复用旧 Oraculum profile。新目录保持当前已有的私有权限、归属与不跟随符号链接保护。

| 数据 | 推荐存储 | 生命周期 |
| --- | --- | --- |
| 当前可见会话、流式 delta、面板/加载状态 | Zustand 内存 | 按原生 ID 合并；刷新时从本地投影和 Gateway 校正 |
| 历史页、已知 thread/turn/item 投影、缓存 revision/cursor | 独立 IndexedDB 历史库 | 有限容量，可清理、失效、重建；缓存丢失不改变 Codex |
| 草稿、阅读锚点、最近选择、主题/布局/通知/身份偏好 | 单独 IndexedDB 本地状态库 | 设备本地权威；清历史缓存不清草稿，不跨端同步 |
| 窗口尺寸及安全恢复主题入口所需的最小配置 | 主进程私有设置文件 | 原子替换；损坏恢复默认窗口而保留原文件供诊断 |
| 凭据 | 主进程系统密钥服务保护的存储 | 主动撤销/重新配对后替换；历史库重建不影响凭据 |
| 已准备/未知写入的 `operationId`、请求摘要、目标与状态 | 主进程独立持久记录，发送前原子落盘 | 不参与缓存 LRU；崩溃、清缓存后仍先查询 Gateway/原生结果，不自动重发 |

缓存键至少包含 **规范化 endpoint（Origin + Base Path）、Gateway `installationId`、`deviceId`、`projectId`、`threadId`**；页面再按 `turnId/itemId/revision` 索引。单用户产品不建立额外账户系统。原生登录/可见性变化时重新取 capabilities 和会话列表，防止把旧可见性当成当前授权。

客户端本地记录还区分缓存版本与 Gateway 事件 `epoch/seq`。Gateway 更换 installationId 后原缓存不能嫁接到新实例；epoch 变化、回放窗口失效、原生压缩/回退/删除触发相应页失效与快照校正。先显示旧内容时必须标为缓存/待校正，审批按钮和写操作须等待当前授权、能力及会话状态确认。缓存损坏只重建缓存库，不触碰草稿库、未知操作记录或 Codex 数据。

流式文本按短间隔合并写入，完成事件立即提交最终投影；不把每个字符变成一次磁盘事务。读取使用分页和可见区域虚拟化；测量长会话的首屏时间、内存和缓存量后确定容量上限，不能在 Phase 0 虚报性能收益。

关闭最后一个窗口后退出 Desktop；不新增 Tray 或隐形永久后台进程。最小化且进程仍在时可发原生通知；退出期间 Codex 的执行由 Gateway/官方 App Server 管理，重开后查询当前状态。恢复主题的原生菜单/快捷键继续独立于 CSS，可在 renderer 加载前选择默认主题。

### 2.4 Trusted CSS Themes 在 Desktop 本地闭合

保留 [docs/THEMING.md](../../docs/THEMING.md) 的 Theme API v1 安全契约，现有 CSS 包校验、受限 MIME/路径和失败回退逻辑作为复用来源。内置主题成为 Desktop 只读资源；新安装的可信自定义包存入 Desktop 私有目录。选择与安装分离，安装不自动应用；不从旧 Bridge 状态复制主题或偏好。

主题素材由 Desktop 的受限本地资源处理器提供，不继续依赖 Gateway 主题路由；CSS 保留清晰的包根和相对资源改写。主题只改变 CSS/素材，不承载 React/JS，不能获得 IPC 或主机能力。Android 以 Compose 的已定稿设计系统实现外观；CSS 包不是跨端主题同步协议。涉及原主题能力在 Compose 中的产品取舍，应按 Android 设计章的冲突项审阅。

## 3. Gateway、CLI 与 DEB 全新安装方案

### 3.1 命名与目录推荐

| 对象 | 推荐名称/路径 | 用途 |
| --- | --- | --- |
| Gateway Debian 包 | `oraculum-gateway` | 自包含 Node 运行时、Gateway/CLI、许可证和服务单元 |
| 用户 CLI | `/usr/bin/oraculum` | 状态、初始化、配对、设备列表/撤销 |
| Gateway 服务程序 | `/usr/bin/oraculum-gateway` → `/usr/lib/oraculum-gateway/…` | user systemd 的稳定启动入口 |
| 用户服务单元 | `oraculum-gateway.service` | 以已有 Ubuntu 用户运行；不新建系统账户 |
| Gateway 配置 | `$XDG_CONFIG_HOME/oraculum-gateway/config.json` | 新配置；Origin/Base Path、端口、工作目录及 Codex 路径等显式输入 |
| Gateway 状态 | `$XDG_STATE_HOME/oraculum-gateway/` | 新 SQLite、附件/成果元数据等；文件权限 0600、目录 0700 |
| Desktop Debian 包/程序 | `oraculum-desktop` | 独立 Electron 和完整 UI 资源；桌面菜单名称仍为“神谕” |
| Desktop profile | `$XDG_CONFIG_HOME/oraculum-desktop-v2/` | 与旧 profile 分离的全新凭据、偏好与缓存 |

现旧 Desktop 拥有 `/usr/bin/oraculum`。新 Gateway 包不能用 `--force-overwrite` 抢占。推荐在未来正式安装前检查包文件所有权，先由用户按已批准安装计划移除冲突的旧程序包（不 purge 用户数据），再安装新包；打包依赖关系须使冲突显式失败，不以 maintainer script 隐式卸载/迁移旧包。新包无需提供 `oraculum-bridge` 别名或旧 Cookie/协议兼容。

### 3.2 最小 CLI

| 命令建议 | 行为 |
| --- | --- |
| `oraculum init` | 仅在选定的新私有路径创建最小配置/新库；若路径已含旧格式或不安全权限则停止；不启动服务、不导入旧数据 |
| `oraculum status` | 显示包/协议版本、选定新配置、Gateway/Codex 连通性及脱敏状态；不输出凭据、配对码或会话正文 |
| `oraculum pair` | 创建限时一次性配对码，只在本人本地终端展示；有过期、尝试次数和单次消费约束 |
| `oraculum devices list` | 展示设备名称、标识、创建/最近使用和撤销状态 |
| `oraculum devices revoke <id>` | 通过同一数据层事务撤销设备；Gateway 对新请求和现有 WSS 及时生效 |

单用户低并发场景下，CLI 使用共享 store 模块直接访问同 UID 私有 SQLite，只做短事务并设置忙等待；先校验 schema，所有写入沿用 Gateway 的同一校验规则。无需额外 Unix socket 管理服务或管理令牌体系。Gateway 不能将“曾通过验证”永久缓存为授权：每次请求检查设备状态，现有连接在事件发送前及定时检查撤销；详细约束以通信/认证规格为准。

### 3.3 服务与全新安装步骤

沿用现包“程序、配置、状态分开”的原则，DEB payload 不附用户配置、数据库、Codex 二进制或私有部署入口；使用固定摘要核验的私有 Node runtime、锁定依赖及完整许可证。Gateway 对官方 Codex 的路径/版本作检查，不替用户安装、覆盖或配置 Codex。

推荐 user systemd 保留 `Type=simple`、`UMask=0077`、`Restart=on-failure` 和有界启动重试；单元直接执行打包的 Gateway 入口，不从可写目录加载代码。Gateway 启动前完成配置/状态版本检查；退出时将无法确认结果的操作保留为未知。不能为加固单元而未经验证限制 Codex 必需的主机工具或擅改原生权限配置。现单元是研究参考：[packaging/oraculum-bridge.service](../../packaging/oraculum-bridge.service)。

未来全新部署按以下顺序执行，每个步骤有独立结果记录：

1. 读取已审阅版本和产物清单，核验包名、架构、源码 SHA、摘要、协议及状态 schema；保护旧包、旧 Oraculum 文件、Codex 原生目录和其他服务。
2. 完成包文件冲突预检与明确的新目录/端口选择；端口是部署输入，不能假定某个私有实例端口空闲。
3. 安装新 Gateway/Desktop 程序包。包安装不自动 enable/start/restart 单元、不登记公网入口、不读取旧库。正式 DEB 安装仍需相应授权。
4. 通过新配置初始化 Gateway；检查配置、数据库和 `installationId` 都是新生成，且未导入旧配对、项目注册、回执或偏好。Codex 原生项目可由用户在新界面重新注册，原生会话通过官方接口发现。
5. 在服务启用授权范围内加载并启动 `oraculum-gateway.service`；验证 readiness、官方 Codex 连通性和明确失败提示。自动登录后运行是否 enable 由部署计划写明，不更改用户全局登录策略或 linger。
6. CLI 生成配对码，客户端按新身份配对；验证撤销及重新配对。Desktop 使用 loopback，Android 使用配置的 HTTPS/WSS endpoint；Base Path 默认 `/`。
7. 如需既有远程链路改接，另列确切代理/隧道影响、备份和回滚计划，并获得对应授权后执行。包安装及 Git 推送都不授权网络改动。

本次 Phase 0 没有执行上述步骤，也没有停止旧 Desktop/Bridge。已批准允许停旧神谕不代表允许删除旧文件；当前研究无需停服。

## 4. 三组件版本、后续更新与回滚

### 4.1 相互独立的版本轴

Gateway、Desktop、Android 各自使用独立 SemVer、变更记录与候选产物；Android 另有全局单调递增 `versionCode`。产品名“2.0”不要求每个组件的版本号总是相同。发布元数据统一从已提交 main 生成，具体首版号在构建任务内确定，本阶段不修改 `release.json`。

| 元数据 | 目的 |
| --- | --- |
| `component`、`version`、`sourceGit`、`sourceDirty: false` | 确认组件与可追溯构建来源 |
| `artifacts[].name/size/sha256`、架构、许可证清单 | 校验候选包；摘要验证完整性，可信发布来源另行校验 |
| `protocol.major/minor` 与最小客户端 minor、能力集合 | 协议协商与功能可用性；不以字符串比较组件版本代替协议判断 |
| Gateway 的 schema 读/写范围 | 判断新版自身状态能否被候选程序读取，防止危险二进制回滚 |
| Desktop/Android 的本地 schema 版本与读范围 | 区分可重建历史缓存和不可静默丢弃的草稿/未知操作 |
| Android applicationId、versionCode、正式证书 SHA-256 | 保证原应用身份、版本单调和原长期签名一致 |
| 已验证 Codex 版本/协议来源及能力限制 | 说明适配器实际验证范围，不把全部生成类型宣称为稳定 API |

协议握手采用 `/api/v2/capabilities` 的 `protocol: {major: 2, minor: 0, minClientMinor: 0}`、`gatewayVersion`、`installationId`、`epoch`、`codex` 和 `limits`。首版只支持 major 2；以后同 major 的可选字段/能力增加允许兼容演进。未知可选字段可以忽略；未知关键事件、必须字段/枚举或需要更高 minor 的写能力不能猜测执行。协议 major 不匹配时客户端可显示已有离线内容与明确更新提示，但禁用在线操作。旧 Bridge 协议 1 无兼容承诺。

### 4.2 新版自身更新流程

采用系统 APT/dpkg 的薄安装/更新流程，不自建常驻更新服务。Electron 官方明确说明 Linux 不提供内置 autoUpdater，推荐使用发行版包管理器：[Electron autoUpdater](https://www.electronjs.org/docs/latest/api/auto-updater)。Desktop 不依赖 Gateway 的特定包版本，缺少或不兼容 Gateway 时显示连接/更新状态；更新客户端资源不自动重启 Gateway。

更新顺序由真实兼容矩阵决定。若新 Gateway 同时支持已安装客户端与新客户端，先 Gateway 再逐端更新；若协议 major 改变，安排明确维护窗口统一切换，不要求旧新版并行或零停机。每次只更新计划内组件，完成其验证后再继续。

Gateway 更新前先停止接收新写入，等待当前操作可确认或明确显示仍有未知结果，再在授权窗口停止新 Gateway。对 **2.0 自身**状态、配置、当前包和 manifest 做一致备份；SQLite 使用 backup API 或已验证的完整停机备份方式，不能仅拷贝遗漏 WAL 的主文件。新版本先在副本上校验 schema 及必要的新版内部升级，最后替换程序和按计划启动；这不是旧版应用状态迁移。

程序失败时只有在旧 2.0 程序支持 **当前最新状态** 的情况下才允许二进制回滚。不能把旧状态快照覆盖当前库来恢复已撤销设备、丢失未知写入或回执；不兼容时保留最新库并停止自动回滚，修复兼容版本。Gateway 重启导致客户端 epoch 改变，必须先对账，不能恢复本地“发送中”后再次发送。

Desktop 更新只替换本组件程序资源，保留 2.0 本地草稿、凭据及未知操作记录。历史缓存 schema 不兼容时可局部重建；草稿/未知操作格式不兼容时停止破坏性降级，不能把“缓存可删”扩大为删除全部 profile。还原旧 Desktop 包不改 Gateway 数据，不触碰官方 Codex 配置或会话。

### 4.3 Android：同身份全新安装与后续维护

首个 Compose 正式版继续使用 `dev.oraculum.poc` 与原长期证书。原证书承担应用身份，**不要求沿用旧 WebView Cookie、SharedPreferences、数据库或配对**。采用新命名的 Room/DataStore/Keystore 项；即使用户误将同签名新版覆盖安装到旧应用上，新代码也不读取旧命名空间，不把旧信任当作新版配对。推荐正式部署由用户完成已约定的清除旧应用状态/重新安装，然后重新配对；实际卸载/清除操作须包含在安装授权内。

重新安装可能触发系统备份还原，不能只依赖“卸载了”推断干净初始状态。实施时明确禁用/排除凭据、配对、数据库及偏好备份，覆盖 cloud backup 与 device transfer 规则，并在真机验证厂商行为；新客户端只认 2.0 初始化标识与新凭据。Android 官方说明默认备份范围包含偏好和数据库，并提供排除/禁用机制：[Auto Backup](https://developer.android.com/identity/data/autobackup)。

构建过程先产生独立 unsigned APK，再由现有 launcher 读取原 Secret Service 凭据执行签名。收到后续“签名 APK”或“构建并发布 APK”指令后，按仓库规范执行 `python3 scripts/android-signing.py release --auto`（已有已审阅 unsigned 包可加 `--apk`）；不再次索要密码、哈希或签名授权。缺失凭据、证书或完整性不符则安全停止。JKS、证书、离线备份及现有正式 APK 保持原样；密码只经 apksigner stdin，不能进入 Gradle、参数、环境变量或明文文件。签名/产物交付不自动授权安装、配对状态清除或正式服务变更。依据：[现有签名脚本](../../scripts/android-signing.py)、[Android 签名规则](https://developer.android.com/studio/publish/app-signing)。

后续 2.0 更新才维护新版自己的 Room/DataStore schema 与凭据。Android 正常安装受 versionCode 防降级限制；不能承诺直接覆盖安装较低版本即可回滚。推荐发布较高 versionCode 的修复版本，或在单独明确数据损失和重新配对步骤后由用户重装兼容旧版；不绕过系统降级保护。依据：[Android Versioning](https://developer.android.com/studio/publish/versioning)。

## 7. 关键风险、回退与审阅出口

| 风险 | 处理及回退 |
| --- | --- |
| 旧 GUI 的 `oraculum` 文件名与新 CLI 冲突 | 新 Desktop 程序命名分离；首次安装显式检测旧包，按授权处理程序文件，不强制覆盖或暗中迁移 |
| 独立资源引入 preload 后扩大权限 | 主进程只暴露固定业务方法，sender/Schema 双校验；出现任意 IPC/路径访问即阻断 P4 交付 |
| 清缓存顺手丢失未知写入或草稿 | 两类持久数据与可丢弃历史分开；发送前持久 operationId；缓存重建测试必须覆盖未决写入 |
| Gateway 更新回滚恢复旧配对/撤销状态 | 保留最新库，仅在 schema 兼容时回退程序；不兼容则停服修复，不自动覆盖旧快照 |
| 同 Android 身份导致系统恢复旧偏好 | 全新存储命名空间、备份/设备转移排除及真机验收；重新配对，不读取旧 WebView 认证 |
| Android 系统省电与通知权限导致提醒不足 | 真实设备测试并明确可达范围；保留前台恢复与结果补查，不许用“始终在线”掩盖平台限制 |
| 官方稳定 API 无法覆盖某项既有能力 | 按原生能力矩阵报告受限项；由用户决定接受暂缺或另行研究，不自动开启 experimental 或替代执行系统 |
| 文档方案与实际私有部署差异 | 正式安装前形成实例化计划；公共仓库只保存可移植参数和通用步骤，不带入私有网络默认值 |

真正需要用户在 Phase 0 审阅时决定的是：是否接受整套架构规格及 Phase 1–5 顺序，以及功能/设计章节中已明确列出的产品取舍和稳定接口受限项。目录名、IPC 方法实现、缓存批次等在接受本建议后可由工程验证收敛，不再拆成无必要的确认问题。正式安装、服务启用、APK 安装/清状态、公开软件发行与网络变更是之后任务的授权边界，不能混作本阶段已经批准的操作。
