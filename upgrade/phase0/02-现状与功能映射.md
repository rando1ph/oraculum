## 1. 结论

现有后端已具备适合作为新 Gateway 基础的 Codex App Server 适配、项目授权、发送回执、附件/成果访问、原生审批与断线恢复语义。需要拆开的主要部分是 HTTP Cookie 与共享 Web UI 的绑定、后端主题资源托管、Desktop 加载 Bridge 页面、Android WebView，以及前端页面内集中的连接和状态管理。没有证据支持重写 Harness 或改用另一套模型执行系统。

“独立双 DEB”已经实现，但客户端尚未独立拥有完整 UI：Bridge 构建仍复制 React Web 产物与主题；Desktop 依旧加载回环地址；Android 的核心页面依旧由 WebView 加载服务器资源。2.0 的新工作是应用边界解耦与原生 Android，不是再次拆一个安装包。

旧状态库包含 **9 张长期业务表**，保存信任、项目身份和可靠通信元数据；没有权威消息表、完整历史缓存表、持久审批表或成果内容表。数据和表结构都不迁移；可复用的是经验证的安全约束与业务规则。已有事件回补、内存投影、草稿和阅读位置持久化，也不能等同于 2.0 要求的双端持久历史缓存。

## 5. 必须保留的安全与可靠性语义

### 5.1 Codex 权威与请求边界

原生启动使用用户既有 Codex 可执行程序及其配置解析，不覆盖 `CODEX_HOME` 或自行注入模型执行系统。仅暴露审阅过的方法；原生新增字段不应导致整个系统无理由拒绝工作，但关键身份、状态、权限字段必须验证。当前构建 schema 锁定与运行时兼容检查已经分离；生成类型存在不等于运行时稳定 API。[codex.ts:24](../../bridge/src/codex.ts#L24)、[compatibility.ts:12](../../bridge/src/compatibility.ts#L12)、[generate-protocol.mjs:7](../../scripts/generate-protocol.mjs#L7)

当前 `ReadQueries` 将 `thread/resume` 归入恢复查询，但禁用相同请求合并；其语义包含恢复原生订阅/线程加载，不应在 2.0 泛化为任意无副作用 GET。新的读写分类需要逐方法审阅，不能机械复制旧 `nativeReads` 集合。[read-queries.ts:4](../../bridge/src/read-queries.ts#L4)、[service.ts:84](../../bridge/src/service.ts#L84)

### 5.2 未知写入不是失败

有副作用调用在断线、超时、响应 shape 不兼容或进程退出时可能已经发生。当前实现让发送回执先持久落盘，并把未知状态与原生明确拒绝区分；读查询可有限重试，写请求不自动重发。[codex.ts:88](../../bridge/src/codex.ts#L88)、[receipts.ts:21](../../bridge/src/receipts.ts#L21)、[client.ts:77](../../packages/shared/client.ts#L77)

当前账本尚未统一覆盖 `thread/start`、归档/恢复/删除、interrupt、审批响应等全部副作用路径；某些生命周期未知状态只在 `BridgeService` 内存中。推荐新协议为所有有副作用请求明确操作 ID、设备归属和可证明的对账规则，禁止靠“原生现在空闲”推断某条未知请求未执行。应保存最小通信元数据，避免把提示词、审批内容和工具输出变成 Gateway 权威记录。

### 5.3 授权、主机文件与传输

当前 HTTP/WS 检查精确 Host、Origin、HTTPS 代理协议与 Base Path；远程必须 HTTPS，进程只监听回环；Cookie 为 HttpOnly/SameSite，远程 Secure；请求、事件和长传输会重新检查撤销。新原生认证虽然要替换 Cookie 耦合，仍需保持同等撤销及时性、边界校验和传输保护。[server.ts:29](../../bridge/src/server.ts#L29)、[server.ts:88](../../bridge/src/server.ts#L88)、[server.ts:301](../../bridge/src/server.ts#L301)、[main.ts:59](../../bridge/src/main.ts#L59)

主机文件不能仅用字符串前缀检查。现有项目 realpath/inode 校验、Linux 文件描述符相对访问、`O_NOFOLLOW`、单硬链接/普通文件检查、目录替换复核、内容类型/大小限制、并发/速率限制均有实际作用。附件的“设备 + 项目 + 会话 + 草稿”归属、成果的短期文件版本授权应保留。不能为了让 Android 能选文件而开放任意主机绝对路径、隐藏配置文件或 JS 到 OS 的通用桥。[attachments.ts:21](../../bridge/src/attachments.ts#L21)、[attachments.ts:168](../../bridge/src/attachments.ts#L168)、[artifacts.ts:22](../../bridge/src/artifacts.ts#L22)、[artifacts.ts:49](../../bridge/src/artifacts.ts#L49)、[artifacts.ts:158](../../bridge/src/artifacts.ts#L158)

### 5.4 历史、事件与 UI 恢复

元数据就绪、历史已加载、WS 连接成功与 Codex 可响应是不同状态。当前元数据优先恢复及有界展示避免历史读取卡住全部交互；event seq 出现缺口时重同步，不能直接继续拼接 delta。原生快照与本地实时投影合并时，终态不得被较旧 running 覆盖，回退/压缩必须使旧页和旧响应失效。[main.tsx:470](../../apps/web/src/main.tsx#L470)、[store.ts:66](../../apps/web/src/store.ts#L66)、[store.ts:130](../../apps/web/src/store.ts#L130)

当前 `history.ts` 尝试原生 `thread/turns/list` 和 `thread/items/list`，在已知 unsupported/experimental 等错误时回退到 `thread/read(includeTurns=true)`，再由 Bridge 做界面分页。后者每次仍可能读取完整原生历史；“前端每页 5 个 Turn/40 个 Item”不是原生 IO 已有界的证明。2.0 应依官方稳定接口审核结果选定路径，并明确超长历史的超时/内存风险，而非承诺无限历史秒开。[history.ts:30](../../bridge/src/history.ts#L30)、[history.ts:53](../../bridge/src/history.ts#L53)、[history.ts:108](../../bridge/src/history.ts#L108)

### 5.5 客户端与主题

Electron 已关闭 Node integration、开启 context isolation/sandbox/webSecurity，下载与权限受限；独立 UI 后不能为了方便连接而放宽这些限制。[main.cjs:17](../../apps/desktop/main.cjs#L17)

按最新结项裁定，Desktop 必须具备基本可用外观及恢复能力，旧 Trusted CSS Themes、Theme API v1、四套主题及历史偏好无迁移义务；高级可导入主题或复用旧主题系统均为另行决定的可选范围。若选做可信 CSS，仍须明确安装、安全素材校验与失败回退，不能升级为 JS/React 插件。Android 原生 Compose 按同一 Stitch token 实现 Light/Dark/OLED Dark，主题/字体偏好属于本地状态；不执行 CSS/DOM 包，不另做衍生设计稿。[docs/THEMING.md:164](../../docs/THEMING.md#L164)、[docs/THEMING.md:182](../../docs/THEMING.md#L182)

## 7. 复用顺序、关键缺口与验收建议

推荐先提取可独立测试的 Codex 适配与项目/文件安全规则，再实施新 Gateway 契约和状态库，随后完成 Android 核心链路。Desktop 继续沿用 React/Zustand 与现有 Markdown、Diff、过程组件，主题组件仅按实际选做范围复用，避免将 Android 重写变成双端 UI 同时全部重写。`service.ts` 与 `main.tsx` 的体量意味着逐职责拆分是维护工作，但没有理由先建设通用微服务、插件框架或第二套状态权威。

| 风险/缺口 | 为什么需要单独处理 | 建议验收证据 |
| --- | --- | --- |
| 旧 TypeScript 协议直接传播 Codex 形状 | Kotlin 不应依赖 TS 编译输出，也不能把全部原生字段默认公开 | 正式 Schema 编译生成双端类型；实际 JSON fixture 双向兼容；未知可选字段/枚举的降级测试 |
| 旧 Cookie/同源模型不等于原生客户端认证 | 原生 HTTP、WS、Keystore、续期、撤销需要独立设计 | 真机配对、重启、续期、撤销、入口变更、无效证书；泄漏检查和跨设备拒绝 |
| 持久历史缓存尚未实现 | 现有缓存主要为运行内存，网页资源缓存不是会话缓存 | 已加载历史在杀进程后离线只读；联网校正、删除/回退/压缩失效、损坏重建；草稿独立保留 |
| 账本不覆盖所有副作用 | 新建/生命周期/审批等断线后存在独立未知窗口 | 每类写操作的“提交前/原生接受后/响应前/重启”故障矩阵；没有重复原生调用 |

| 通知和恢复依赖平台生命周期 | WebView 当前 Cookie 转交和 2 秒轮询不能直接照搬 | 必测真机前台、按 Home 返回桌面后提醒及点击恢复；过期审批不可操作；锁屏/Doze/强杀只记录限制或选测，不要求通知必达；缓存进程重启恢复单独验收 |
| 主题退出 Gateway | 当前主题由后端安装与托管；新 Gateway 不承担 UI 外观 | Desktop 基本外观可恢复；若选做高级主题再验证资源隔离，旧四套主题 / Theme API v1 不设强制迁移验收 |
| 旧安装路径/状态选择保护包含历史迁移分支 | 全新 2.0 已取消旧数据兼容，直接复制启动逻辑会把旧路径重新引入 | 新独立空状态路径启动；无旧库/配置读取；原 Codex 配置/会话和其他服务前后保持 |
| 独立版本不代表接口天然兼容 | 当前构建检查仍固定协议 1，不能改名即宣称支持新协议 | 三组件新版本矩阵、最低/最高协议拒绝行为；干净源码构建、产物身份/hash、全新首次配对 |

这些缺口属于已批准架构下的工程设计与验证任务，原则上无需让用户重新选择 Electron、Android 技术栈、Gateway 名称或是否迁移。总体方案和稳定 API 受限时的明确降级已被接受，Phase 1 已独立授权；本文保留研究证据，不代表后续实现或验收已经完成。
